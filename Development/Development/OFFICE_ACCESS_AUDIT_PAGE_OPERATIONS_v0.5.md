## 2. Особые выводы, которые нельзя потерять при проектировании матрицы

1. **`revenue.html` не вызывает `requireAuth()`.** Страница читает `income_entries` и рассчитывает сводный доход по всем направлениям. Это реальная финансовая сводка, а не просто публичный экран.
2. **`store.html` — публичная витрина, но пишет в `income_entries`.** Публичный заказ нельзя просто закрыть вместе с финансовой таблицей: потребуется безопасный серверный путь оформления заказа, который принимает только необходимые поля и сам формирует финансовую запись.
3. **`atelier.html` совмещает публичное оформление заказа с прямыми операциями склада и финансов.** Клиент читает `avg_unit_cost`, меняет `warehouse_stock`, добавляет `warehouse_movements` и записывает `income_entries`. Это следует перенести за контролируемую серверную границу; публичный заказ не должен иметь прямого доступа к учётным операциям.
4. **`suppliers.html` вызывает `receive_supplier_order`.** По ранее проверенному определению RPC он доступен роли `authenticated`, но в теле не найдено явной проверки OFFICE-разрешения. Наличие Auth-сессии не должно означать право принять поставку и сформировать расход.
5. **`atelier-space.js` работает fail-open:** если чтение `moon_modules` завершается ошибкой или запись отсутствует, функция `allowed()` возвращает `true`. Это может быть сознательным UX fallback, но не должно использоваться как механизм безопасности.
6. **`modules/paymentTerminal.js` — только имитация.** Код показывает TAP/PROCESSING/APPROVED и формирует локальную PNG-квитанцию; комментарий прямо говорит, что реальные карты не принимаются и деньги не перемещаются. Это не реальный платёжный процесс.
7. **Публичные модули отзывов, форума, De-Stress и заявок** требуют отдельного публичного набора ограниченных операций, а не предоставления широкого CRUD по базовым таблицам.

## 3. Страницы без прямых Supabase-вызовов в статическом сканировании

Отсутствие прямого `.from()`/`.rpc()` в HTML не доказывает отсутствие доступа: страница может импортировать общий модуль или быть только навигационной. В частности, `accounting.html`, `office.html`, `identity.html`, `hall.html`, `entrance.html`, `payment-terminal.html` и другие страницы требуют проверки импортов и пользовательских сценариев. Для `income.html` и `income-store.html` прямые запросы в самом HTML не обнаружены; права по названию страницы не назначались.

## 4. Что ещё не закрыто

- Не выполнен полный динамический тест каждой кнопки/формы в браузере и не проверены все ветви условий.
- Не все страницы проверены на транзитивные импорты общих модулей; инвентарь содержит и отдельные модули, чтобы не потерять их операции.
- Не определены окончательные роли и разрешения для каждой операции: это следующий этап после подтверждения бизнес-сценариев.
- Будущие Пусковые Комплексы должны подключаться через единый реестр комплекса/модуля и назначаемые разрешения, а не получать автоматический доступ ко всем таблицам.
- `launch_complexes` в текущем коде обслуживает конфигурацию комплексов; сам факт наличия записи о комплексе не должен давать доступ к его административным операциям.

## 5. Рекомендуемый следующий результат

Сформировать нормализованную матрицу **страница → пользовательский сценарий → операция → объект данных → кто может выполнять → ограничения полей/строк → серверная точка контроля → аудит-событие**. Для публичных сценариев выделить ограниченные RPC/Edge Function или безопасные представления. Для OFFICE — проверку роли и конкретного permission на сервере/RLS, включая область данных и отдельные права на просмотр, создание, изменение, удаление, утверждение и экспорт.

**Важно:** этот документ — инвентаризация исходного кода, а не готовая миграция. Ничего не закрывать массово, пока не будет описан и проверен публичный путь заказов, лайков, отзывов, форума, De-Stress и контента.
