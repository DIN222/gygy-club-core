
# CONTRACT.md — контракт модулей GY-GY Club Core
v1.1.0 — 2026-08-26
Изменения: добавлен п.8 (жизненный цикл виден извне через MODULE_INIT/MODULE_DESTROY).

Версионируется по тем же правилам, что описаны в п.6 ниже (сам контракт применяет
собственное правило к себе). Дата — дата первого создания документа, не обновляется.
При повышении версии контракта уже существующие файлы НЕ обязаны обновляться немедленно —
но при следующей правке любого файла его нужно привести в соответствие актуальной версии
контракта, а не оставлять как есть. Файл, отстающий от текущей версии CONTRACT.md,
не является ошибкой сам по себе — это ожидаемое временное состояние проекта, который
"живёт в реальном времени"; проблема начинается, только если отставание не устраняется
при следующей правке этого файла.

Этот документ фиксирует обязательные правила для любого файла в `core/` и `modules/`.

## 1. Только ES-модули

Каждый файл — `export`/`import`. Никаких `window.X` глобальных объектов.

```js
// Правильно
export function on(event, callback) { ... }

// Неправильно — так делал старый core/eventBus.js
window.EventBus = { ... };
```

Причина: смешение `window.X` и `import` в одном проекте приводило к рантайм-ошибкам
(старый `modules/hall.js` пытался `import { EventBus }` из файла без единого `export`).

## 2. Общение только через EventBus

Модуль никогда не импортирует и не вызывает напрямую функции другого модуля того же уровня
(`modules/` не вызывает `modules/`). Единственный канал — `core/eventBus.js`:

```js
import { emit, on } from '../core/eventBus.js';

emit('PROFILE_SAVED', { id: 'GY-001' });
on('PROFILE_SAVED', (data) => { ... });
```

Исключение: модуль может импортировать `core/*` напрямую (eventBus, storage, localization) —
это инфраструктура, а не «соседний экран».

## 3. Данные — только через Storage

Прямой вызов `localStorage.getItem/setItem` где-либо, кроме `core/storage.js`, запрещён.

```js
// Правильно
import { get, set } from '../core/storage.js';
const passport = get('passport');

// Неправильно — так делал старый modules/hall.js
const isBoss = localStorage.getItem('gygy_is_boss') === 'true';
```

Причина: при изменении схемы хранения (например, версионирование) все места
прямого обращения к `localStorage` придётся находить и чинить вручную.

## 4. Жизненный цикл модуля

Каждый файл в `modules/` обязан экспортировать три метода:

```js
export function init(container) {
    // подписка на события через EventBus.on()
    // рендер разметки внутрь container (не всей страницы!)
}

export function update(data) {
    // реакция на изменение состояния
}

export function destroy() {
    // EventBus.off() для каждой подписки, сделанной в init()
    // очистка DOM внутри container, если нужно
}
```

Каждый `on()` в `init()` должен иметь парный `off()` в `destroy()`. Без этого при повторном
входе в комнату колбэки накапливаются и начинают срабатывать многократно.

## 5. Модуль не владеет всей страницей

Модуль рендерит себя внутрь переданного `container` (DOM-элемента), а не ищет элементы
по всему `document` через фиксированные `id`, которые предполагают конкретную вёрстку.

```js
// Правильно
export function init(container) {
    container.querySelector('.btn-hall').addEventListener('click', ...);
}

// Неправильно — так делал старый modules/hall.js
document.getElementById('btn-w-hall'); // жёстко привязано к конкретной странице
```

## 6. Версия и дата в шапке файла

Каждый файл начинается с комментария:

```js
/**
 * core/eventBus.js
 * v1.0.0 — 2026-08-26
 * Краткое описание назначения файла.
 */
```

Дата — дата ПЕРВОГО создания файла, не обновляется при последующих правках.
Актуальность файла показывает номер версии, а не дата — см. правило версионирования ниже.

Версия повышается при ЛЮБОМ изменении поведения модуля — не только при изменении сигнатуры
функций, но и когда сигнатура та же, а результат работы функции меняется (например, функция
рендерит список и раньше выводила один набор элементов, а теперь другой). Не повышается только
при правках, не влияющих на поведение: опечатки в комментариях, форматирование, переименование
локальных переменных.

Патч-версия (v1.0.0 → v1.0.1) — небольшое изменение поведения в рамках той же логики.
Минорная версия (v1.0.x → v1.1.0) — добавлена новая функция/возможность модуля.
Мажорная версия (v1.x.x → v2.0.0) — изменена сигнатура существующих функций, что ломает
обратную совместимость с уже написанным кодом, который эти функции вызывает.

Каждое изменение версии сопровождается короткой строкой "Изменения: ..." в шапке файла —
не историей всех версий, а только сути последнего изменения (историю версий хранит git).

Это заменяет вручную обновляемый ARCHITECTURE.md — актуальное состояние видно в самом коде.

## 7. HTML-страницы — тонкие

Страница содержит разметку и один `<script type="module">`, который импортирует нужные
модули и вызывает их `init()`. Бизнес-логика (обработка данных, генерация ID, переводы)
внутри `<script>` на странице не пишется — она должна жить в `core/` или `modules/`.

## 8. Жизненный цикл виден извне

`init()` и `destroy()` обязаны эмитить события через EventBus с именем модуля — не только
менять своё внутреннее состояние, но и объявлять о рождении/смерти вовне:

```js
const MODULE_NAME = 'passport'; // совпадает с именем файла в modules/, без расширения

export function init(container) {
    // ...обычная инициализация...
    emit('MODULE_INIT', { module: MODULE_NAME, at: Date.now() });
}

export function destroy() {
    // ...обычная очистка...
    emit('MODULE_DESTROY', { module: MODULE_NAME, at: Date.now() });
}
```

Причина: без этого правила о жизни и смерти модуля знает только он сам — нет способа
увидеть общую картину (сколько модулей сейчас активно, кто из них давно не проявлял
активности, чей "разъём" освободился и готов к переиспользованию). Это станет основой
будущего узла мониторинга в Офисе (см. CONTEXT — идеология "родился/жил/постарел/умер").
Правило вводится сейчас, чтобы не переписывать уже готовые модули задним числом, когда
узел мониторинга появится.
