# GY-GY CLUB — ТЕХНИЧЕСКИЙ РЕЕСТР СОБЫТИЙ
## DE-STRESS STUDIO

**Версия:** 0.1.0  
**Дата создания:** 2026-11-12  
**Статус:** каркас реестра; спецификация не завершена.

> Файл создан как место для следующего этапа работы. Он не содержит неподтверждённой спецификации будущих событий. Наличие события в документе не означает, что оно реализовано.

## 1. Назначение

Реестр описывает события De-Stress Studio: источник, условие возникновения, payload, проверки, получателей, хранение, доступ и реакцию OFFICE.

Он не заменяет:
- `modules/destressStudioEvents.js`;
- `core/eventBus.js`;
- серверные функции Supabase;
- операционные журналы и аналитические хранилища.

## 2. Обязательные поля записи

| Поле | Назначение |
|---|---|
| Event ID | Стабильный идентификатор |
| Event name | Точное техническое имя |
| Смысл | Какой факт подтверждает |
| Статус реализации | Реализовано / частично / предусмотрено / не определено |
| Источник | Страница, модуль, серверная функция или сотрудник |
| Условие | Проверяемое условие возникновения |
| Payload | Разрешённые поля и типы |
| Запрещённые данные | Что нельзя включать |
| Проверка | Клиентская и/или серверная валидация |
| Получатель | EventBus, Supabase, OFFICE, аналитика |
| Хранение | Таблица, журнал или отсутствие постоянной записи |
| Доступ | Кто создаёт, читает или обрабатывает |
| Срок хранения | Утверждённый срок или «не определён» |
| Реакция OFFICE | Требуется ли служебное действие |
| Связанные потоки | ID из матрицы потоков |
| Примечание | Ограничения и открытые вопросы |

## 3. Обнаруженные определения в программном модуле

В `modules/destressStudioEvents.js` v1.0.0 от 2026-11-09 обнаружены:

### 3.1. События жизненного цикла

| Event name | Назначение | Payload |
|---|---|---|
| `MODULE_INIT` | Запуск модуля | module, location, at |
| `DESTRESS_STUDIO_OPENED` | Открытие локации | location, at |
| `DESTRESS_STUDIO_LEFT` | Выход из локации | location, at |
| `MODULE_DESTROY` | Завершение модуля | module, location, at |

### 3.2. Типы событий, разрешённые whitelist в `track()`

| Тип track() | Имя EventBus | Разрешённые поля |
|---|---|---|
| `SITUATION_SELECTED` | `DESTRESS_STUDIO_SITUATION_SELECTED` | kind, source |
| `PHRASE_CREATED` | `DESTRESS_STUDIO_PHRASE_CREATED` | mode, source, isDoubleMix |
| `MATERIAL_SUBMITTED` | `DESTRESS_STUDIO_MATERIAL_SUBMITTED` | materialType, newsRequested, status, language |
| `EXPORT_CREATED` | `DESTRESS_STUDIO_EXPORT_CREATED` | format, theme |
| `ATELIER_REQUESTED` | `DESTRESS_STUDIO_ATELIER_REQUESTED` | ai |
| `SHARE_REQUESTED` | `DESTRESS_STUDIO_SHARE_REQUESTED` | channel |

Модуль копирует только разрешённые поля; строки ограничиваются 40 символами. Пользовательский текст и персональные данные в payload не добавляются.

**Ограничение интеграции:** в проверенном `destress-studio.html` v5.2.0 не обнаружены импорт `destressStudioEvents.js` и вызов `track()`. Следовательно, типы событий определены в сервисном модуле, но передача их из пользовательской страницы не подтверждена. До подключения и проверки нельзя считать их действующим мониторингом страницы.

## 4. Серверные счётчики — не голоса

Supabase RPC `destress_bump(p_id, p_kind)` изменяет счётчики:
- `atelier` → `n_atelier`;
- `order` → `n_order`;
- `share` → `n_share`;
- `download` → `n_download`;
- `copy` → `n_copy`.

В проверенной странице обнаружены вызовы для `copy`, `download`, `share`. Вызовы `atelier` и `order` из неё не обнаружены.

Счётчики не являются лайками или клубными голосами; они фиксируют вызов RPC, а не обязательно завершённое действие. Права EXECUTE и SECURITY DEFINER требуют отдельного аудита до изменения.

## 6. Правила проектирования

1. Событие фиксирует конкретный факт, а не намерение, если его имя утверждает завершение действия.
2. Запрос и успешный результат различаются, если между ними есть проверка или отказ.
3. Не передавать исходный текст, Passport ID и другие персональные сведения в общий аналитический payload без отдельного обоснования.
4. Клиентская эмиссия не является доказательством серверного результата.
5. Голосование, удаление, модерация и полномочия требуют серверной валидации.
6. Определить защиту от повторов, злоупотреблений и некорректного payload.
7. Аналитические события отделять от операционных записей.
8. Не создавать постоянное хранение без определённой цели.
9. Не смешивать события использования с голосованием.
10. Соблюдать `CONTRACT.md` и архитектуру EventBus.

## 7. Порядок заполнения

1. Сверить фактические вызовы в странице и модулях.

4. Определить payload и исключить лишние данные.
5. Определить серверную проверку и источник достоверности.
6. Назначить получателя и место хранения.
7. Установить права доступа и сроки хранения.
8. Определить реакцию OFFICE.
9. Сверить записи с матрицей потоков.
10. Только после утверждения спецификации проектировать изменения кода и Supabase.
