## 1. Назначение документа

Реестр событий определяет, какие события возникают в De-Stress Studio, какие из них регистрируются системой, для каких целей используются и где должны храниться.

Основные задачи:

- обеспечить наблюдаемость работы локации;
- обеспечить контроль операций с публикациями;
- поддерживать модерацию и управление;
- формировать достоверную обезличенную аналитику;
- обеспечивать обратную связь с OFFICE;
- предоставить основу для развития GY-GY NEWS и Книги почёта;
- обеспечить возможность технической диагностики;
- не допускать избыточного сбора персональных данных.

Документ разделяет фактически существующие операции, существующие технические заготовки и целевые механизмы.

**Важно:** наличие пользовательской операции не означает, что для неё уже создана отдельная запись в реестре событий.

## 2. Основные принципы

### 2.1. Разделение событий

Все события разделяются на три основных категории.

**А. Операционные события**

Возникают при работе с конкретными объектами и операциями клуба.

Примеры:

- создание публикации;
- изменение статуса;
- фиксация авторства;
- лайк;
- номинация;
- голосование;
- удаление публикации;
- административное действие.

Операционные события могут содержать технические идентификаторы объектов, необходимые для выполнения операций и контроля их результатов.

Доступ к таким записям ограничивается соответствующими полномочиями.

**Б. Аналитические события**

Используются для изучения общей работы локации.

Примеры:

- открытия локации;
- использование функциональных блоков;
- количество выполненных операций;
- динамика предложений;
- агрегированные показатели активности.

Аналитический контур не должен содержать прямые идентификаторы участников и исходные тексты пользовательских публикаций.

**В. Технические события**

Возникают при работе программных компонентов.

Примеры:

- инициализация модуля;
- завершение работы модуля;
- ошибка загрузки;
- ошибка обращения к Supabase;
- сбой передачи данных;
- ошибка выполнения операции.

Технические события нужны для диагностики и обеспечения работоспособности локации.

Они не должны превращаться в скрытый журнал персональной активности.

### 2.2. Минимизация данных

Система фиксирует только те сведения, которые необходимы для конкретной цели.

Не допускается:

- постоянное отслеживание перемещений конкретного участника;
- скрытое чтение буфера обмена;
- сбор содержимого внешних сообщений;
- создание персональных психологических профилей;
- сбор технических характеристик устройства ради скрытой идентификации;
- объединение аналитических событий с Passport ID без отдельного обоснования;
- хранение исходных текстов частных обращений в аналитическом контуре.

Удаление имени или псевдонима само по себе не гарантирует обезличивание.

Необходимо учитывать возможность идентификации по совокупности признаков, редким событиям и точным временным меткам.

### 2.3. Управление и полномочия AI

AI может:

- анализировать разрешённые данные;
- выявлять тенденции;
- обнаруживать необычные изменения показателей;
- прогнозировать потенциальные проблемы;
- формировать рекомендации;
- объяснять основания своих выводов.

AI не получает права самостоятельно:

- менять статусы публикаций;
- удалять публикации;
- назначать авторство;
- изменять правила голосования;
- принимать административные решения;
- изменять рабочие данные без предусмотренного полномочия.

Операционные и управленческие решения остаются под контролем человека.

### 2.4. Разделение факта операции и факта регистрации события

Для каждого механизма необходимо различать:

1. Пользователь совершил действие.
2. Система обработала действие.
3. Сервер подтвердил результат.
4. Реестр получил и сохранил соответствующее событие.

Эти этапы не следует считать одним и тем же.

Например, отправка предложения в Supabase не означает, что отдельная запись о событии `PHRASE_SUBMITTED` уже создана в операционном реестре.

## 3. Существующая техническая основа

В проекте предусмотрен модуль:

`modules/destressStudioEvents.js`

В его текущем перечне определены следующие события:

| Событие | Назначение |
|---|---|
| `MODULE_INIT` | Инициализация модуля |
| `DESTRESS_STUDIO_OPENED` | Открытие De-Stress Studio |
| `DESTRESS_STUDIO_LEFT` | Выход из De-Stress Studio |
| `MODULE_DESTROY` | Завершение работы модуля |
| `SITUATION_SELECTED` | Выбор ситуации |
| `PHRASE_CREATED` | Создание фразы |
| `MATERIAL_SUBMITTED` | Отправка материала |
| `EXPORT_CREATED` | Создание экспортного материала |
| `ATELIER_REQUESTED` | Запрос действия Atelier |
| `SHARE_REQUESTED` | Запрос на распространение материала |

Наличие определения события в модуле ещё не означает, что событие реально регистрируется и сохраняется.

В проверенной версии `destress-studio.html` v5.2.0 модуль `destressStudioEvents.js` не подключён, а вызовы `track()` отсутствуют.

Поэтому перечисленные события являются технической заготовкой, но не подтверждённой действующей системой сбора событий.

Перед подключением модуля необходимо проверить его актуальное состояние и совместимость с `CONTRACT.md`.

### 3.1. Состояние регистрации событий

| Компонент | Текущее состояние |
|---|---|
| Определения событий в `destressStudioEvents.js` | Существуют |

### 4.1. Требования к операционной записи

Для будущей реализации рекомендуется предусмотреть минимальный набор полей:

| Поле | Назначение |
|---|---|
| `event_id` | Уникальный идентификатор события |
| `event_type` | Тип события |

### 4.2. Подтверждение результата

Реестр должен отличать:

- запрос операции;
- принятие запроса системой;
- успешное завершение;
- отказ или ошибку.

Нельзя считать клиентский запрос доказательством успешного завершения операции.

Для критических действий подтверждением должен быть результат серверной обработки.

### 5.1. Принцип периодной агрегации

Предпочтительная модель — хранить итоговые значения за определённый период.

Например:

- количество открытий локации за день;
- количество операций Double Mix за день;
- количество предложенных фраз за неделю;
- количество одобренных публикаций за месяц.

Не следует создавать постоянный журнал индивидуальных посещений только для того, чтобы затем удалить из него идентификаторы.

Агрегирование должно происходить до передачи данных в аналитическое хранилище.

## 6. Структура аналитического события

Для будущей реализации предлагается единый минимальный формат:

```json
{
  "event_type": "DESTRESS_STUDIO_OPENED",
  "event_category": "analytics",
  "location": "de-stress-studio",
  "event_date": "2026-11-12",
  "period": "daily",
  "value": 125
}
```

Пояснение:

| Поле | Значение |
|---|---|
| `event_type` | Тип аналитического показателя |
| `event_category` | Категория события |
| `location` | Код локации |
| `event_date` | Дата агрегированного периода |
| `period` | Тип периода |
| `value` | Итоговое количество за период |

В данном примере `value: 125` означает 125 зарегистрированных открытий за день.

Это пример архитектурного формата, а не существующая таблица или утверждённая схема Supabase.

В аналитическую запись не включаются:

- Passport ID;
- никнейм;
- ID конкретного участника;
- исходный текст публикации;
- содержание частного обращения;
- постоянный идентификатор устройства;
- индивидуальная временная метка посещения.

Для небольших групп и редких событий необходимо дополнительно оценивать риск обратной идентификации.

Аналитическая запись должна содержать только агрегированный результат.

### 8.1. Авторство

Для новых публикаций предусматриваются поля:

- `author_passport_id`;
- `author_nickname`.

Псевдоним фиксируется как снимок на момент создания публикации.

Изменение псевдонима участника не должно автоматически менять авторство старых публикаций.

Для старых публикаций без подтверждённого авторства обратная атрибуция не производится.

Passport ID в существующей реализации является локальным техническим идентификатором.

Он не подтверждает личность человека и не гарантирует, что один человек использует только один Passport.

Поэтому Passport ID нельзя считать достаточной защитой от повторного участия в голосовании или подтверждением авторства без дополнительных серверных механизмов.

### 8.2. Лайки

Предусматриваются две независимые таблицы:

- `destress_situation_likes`;
- `destress_phrase_likes`.

Один участник должен иметь возможность поставить один лайк одной публикации.

Для этого требуется серверная проверка и надёжное ограничение повторных записей.

Лайки De-Stress Studio не связаны с таблицей `print_likes` и механизмом лайкования принтов клуба.

### 8.3. Номинация и голосование

Порог лайков может открыть автору возможность номинировать публикацию.

Он не означает автоматического признания работы.

После номинации проводится отдельное клубное голосование.

Автор не голосует за собственную публикацию.

Один участник должен иметь возможность отдать один голос за конкретную публикацию в рамках конкретного голосования.

Параметры голосования, пороги признания, продолжительность и правила повторной номинации требуют отдельного утверждения.

### 8.4. Книга почёта

Успешно прошедшие клубное голосование публикации могут попадать в соответствующие разделы:

- «ЭТО КРУТО» — для фраз;
- «ВОТ ЭТО СЛУЧАЙ» — для ситуаций.

Событие признания должно фиксировать результат голосования и факт передачи публикации в соответствующий раздел.

## 11. События использования и счётчики

В таблице `destress_phrases` существуют счётчики:

- `n_atelier`;
- `n_order`;
- `n_share`;
- `n_download`;
- `n_copy`.

Они увеличиваются функцией `destress_bump(p_id, p_kind)`.

Функция обновляет соответствующий счётчик для публикации со статусом `approved`.

### 11.1. Что подтверждают счётчики

Счётчики отражают зарегистрированные вызовы соответствующих операций.

Они не являются подтверждением успешного завершения действия.

Примеры:

- `n_atelier` не доказывает, что результат Atelier был успешно создан;
- `n_order` не доказывает, что заказ был оформлен;
- `n_share` не доказывает, что материал был опубликован или отправлен;
- `n_download` не доказывает, что файл был успешно сохранён пользователем;
- `n_copy` не доказывает, что текст был успешно вставлен в другое приложение.

Счётчики не являются лайками, голосами или оценками качества публикации.

### 11.2. Ограничения существующей функции

Текущая функция `destress_bump` имеет права `SECURITY DEFINER` и доступна для вызова публичными ролями.

Вызов функции не подтверждает реальное выполнение соответствующего пользовательского действия.

Права выполнения и защиту функции необходимо отдельно пересмотреть до использования её данных в управленческой аналитике.

Не следует автоматически считать существующие значения счётчиков достоверной статистикой завершённых операций.

### 11.3. Разделение механизмов

Необходимо сохранять независимость четырёх механизмов:

1. Счётчики использования фраз.
2. Лайки ситуаций и фраз.
3. Отдельное клубное голосование.
4. Подтверждение фактического результата операции.

Смешивание этих механизмов недопустимо.

- пароли;
- токены;
- ключи доступа;
- полные персональные записи;
- тексты частных обращений;
- исходные тексты публикаций, если они не нужны для диагностики.

Предполагается разделение доступа:

- модератор — публикации в пределах модерации;
- сотрудник по обращениям — соответствующие частные обращения;
- аналитик — агрегированные показатели;
- технический персонал — необходимые технические сведения;
- администратор — отдельно назначенные административные полномочия.

Доступ к частным обращениям не должен автоматически предоставляться всем сотрудникам OFFICE.

Существующие широкие политики `authenticated` в Supabase не являются полноценной реализацией такой модели.

### 13.2. AI и управленческие решения

AI может получать только те данные, которые разрешены для соответствующей аналитической задачи.

AI формирует выводы и рекомендации, но не подменяет собой полномочного сотрудника.

Каждое существенное управленческое действие должно иметь определённого ответственного человека и подтверждённый результат.

## 16. Связь с матрицей информационных потоков

Реестр событий не заменяет матрицу информационных потоков.

Документы выполняют разные задачи:

- `DE-STRESS-STUDIO-PASSPORT.md` — назначение, структура, функции и правила работы локации.
- `DE-STRESS-STUDIO-FLOWS.md` — источники, обработка, получатели, хранение и права доступа для информационных потоков.
- `DE-STRESS-STUDIO-EVENT-REGISTRY.md` — перечень событий, их назначение, категории и правила регистрации.

Каждое существенное событие должно соответствовать определённому информационному потоку.

Если в реестре появляется новое событие, необходимо проверить, отражён ли соответствующий поток в `DE-STRESS-STUDIO-FLOWS.md`.

Если в матрице потоков появляется новая операция, необходимо проверить, требуется ли для неё регистрация события.

Все три документа образуют единый архитектурный комплект De-Stress Studio.

## 18. Правило актуализации

При добавлении нового функционального механизма необходимо проверить:

- возникает ли новое событие;
- к какой категории оно относится;
- кто является источником;
- что именно произошло;
- чем подтверждается результат;
- какие данные необходимо зарегистрировать;
- где они должны храниться;

- требуется ли отдельная аналитическая агрегация;
- не создаёт ли регистрация избыточный сбор персональных данных;
- отражён ли соответствующий поток в матрице информационных потоков;
- реализован ли механизм фактически или пока только предусмотрен архитектурой.

Изменения кода должны сопровождаться актуализацией настоящего документа.

Нельзя описывать целевой механизм как уже действующий.

Нельзя считать наличие определения события в коде доказательством его фактической регистрации и сохранения.
